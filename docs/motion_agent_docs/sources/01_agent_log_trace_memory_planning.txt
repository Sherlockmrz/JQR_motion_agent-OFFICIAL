2. Agent 内置`trace_id` 评分系统

trace_id 的作用是把一次任务从 8766、Motion Agent、8000 VLN、ROS2、最终 response 串成一条链。评分系统则是在这条链结束后，判断这次任务“做得好不好、哪里不好、下次应该改什么”。
目标
找人找物任务失败时，现在只能看到：
{
  "success": false,
  "error_msg": "",
  "type": "go_find_person"
}
有 trace 和评分后，Agent 能给出：
这次任务 72 分
主要问题：最终 response 不明确
失败阶段：response_normalize
建议：统一 success/result/error_msg/err_msg 字段映射

每次任务进入 websocket_control_server.py 时生成或继承 trace_id：

隐私与内部自学习：trace 默认不直接给人看， 等轨迹出来

实际运用中，每个 trace 可能包含比较敏感的信息，例如用户原始语音文本、目标人名、摄像头识别结果、机器人所在位置、设备 IP、失败时的原始返回、甚至某些多模识别摘要。所以更合理的方式是：
原始 trace：Agent 内部可见，用于评分、复盘和策略学习
脱敏 view：人和上层系统可见，只展示阶段、分数、错误类型和建议

Agent 怎么自学习
让 Agent 根据 trace 评分更新自己的记忆、视图和策略：
执行任务 -> 生成 trace -> 内部评分 -> 写入 AgentMemory -> 更新 Views -> Policy 改变下一次动作

例子 ：8000 VLN 连续连接失败。
第 1 次 trace：VLN_CONNECT_FAILED，score=45
第 2 次 trace：VLN_CONNECT_FAILED，score=42
第 3 次 trace：VLN_CONNECT_FAILED，score=43
AgentMemory 生成 view：
{
  "view_type": "recent_failure_view",
  "task_type": "go_find_person",
  "top_failure": "VLN_CONNECT_FAILED",
  "count_last_3": 3,
  "suggestion": "下次导航前先做 VLN 健康检查"
}
Policy 改变下一次动作：
以前：收到 go_find_person -> 直接发给 8000
Policy：收到 go_find_person -> 先检查 8000 是否可连接 -> 不可连接则直接返回明确错误
例子 2：目标找不到。
最近 3 次找张三都是 TARGET_NOT_FOUND
Agent 学到的策略：
以前：继续重复“找张三”
Policy：先读 target_context_view，看张三最近是否有有效位置；没有就让交互 Agent 追问“张三今天穿什么衣服/大概在哪里”
3. 可以更快复盘。
4. AgentMemory 可以把评分低的 trace 变成失败记忆。
5. Skills 可以把评分高、复现稳定的 trace 变成可复用流程。
6. 原始 trace 默认只在 Agent 内部用于评分和自学习，外部只暴露脱敏 view，减少隐私风险。

目标：生成 Agent 决策模型的 RL 数据集在agent内部自训练（修正）

3. Agent Planning

LLM拆任务，先做意图识别理解，分类（简单任务/复杂任务）调研现在的agent比如codex，Claude code是怎么做这种agent planning的 
边界
Motion Agent 
输入
接收上层交互 Agent 的结构化 intent 或自然语言兜底结果
规划
拆成子任务、判断依赖、选择工具、确定执行顺序
执行
调用 VLN、ROS2、本地动作、状态查询、停止任务
反馈
返回 plan 状态、当前 step、失败原因、需要上层追问的信息
安全
任何时候 stop/emergency_stop 优先，危险动作必须被拦截
整体流程可以是：
用户复杂指令
  -> 交互 Agent / Motion Agent 得到文本或 intent
  -> Planner LLM 生成 Plan 草稿
  -> PlanValidator 校验字段、安全、工具可用性
  -> PlanExecutor 按 step 执行
  -> 每一步写 trace
  -> 失败时 RecoveryPolicy 决定重试、追问、停止或重规划

S1 查询天气
这是信息任务，不需要 VLN。如果 Motion Agent 以后接了天气工具，就直接调用；如果没有天气工具，就向上层交互 Agent 返回一个 need_external_info 请求。
{
  "type": "need_external_info",
  "field": "weather",
  "question": "请查询当前城市是否下雨"
}
成功标准：
拿到 weather.rain = true/false
或者 rain_probability >= 某阈值
S2 进入屋内
这是运动任务。是否接 VLN 取决于屋内目标是否明确：
有固定房间点位 -> 本地导航/Nav2
没有固定点位，需要视觉找门/进屋 -> VLN
成功标准：
机器人到达屋内目标点
或 VLN 返回进入完成
或 ROS2/Nav2 返回 success
失败处理：
目标点不存在 -> 询问上层“具体进哪个房间”
Nav2 timeout -> 标记为导航/底盘问题
VLN_CONNECT_FAILED -> 先检查 8000
S3 寻找张三
这是视觉导航任务，通常接 VLN：

  "type": "go_to_person",
  "user_prompt": "请在屋内寻找张三",
  "person_id": "张三"
}
成功标准：
找到张三
或到达张三附近
或识别模块确认目标出现
失败处理：
TARGET_NOT_FOUND -> 询问衣着/位置/更多描述
连续找不到 -> 换搜索区域或结束并返回明确原因
只收到 command 没有 final -> 等待 final，超时返回 FINAL_RESULT_TIMEOUT

S4 提醒
这是条件任务
如果 weather.rain == true 且 person_found == true -> 执行提醒
如果 weather.rain == false -> 不提醒带伞，返回“天气不下雨，无需提醒”
如果 person_found == false -> 不提醒，返回“未找到张三”

S5 提醒张三带伞
Motion Agent返回给交互 Agent：
{
  "type": "notify",
  "target": "张三",
  "message": "张三，今天可能下雨，出门记得带伞。",
  "delivery": "tts_or_upper_agent"
}
成功标准：
上层交互 Agent/TTS 确认收到提醒请求

 Agent Memory 系统需要解决四个问题：
策略
问题

当前 AgentMemory是过程记录，还不是完整记忆系统。后续要让它参与真实决策：
如果最近 3 次都是 VLN_CONNECT_FAILED -> 先检查 8000
如果最近 3 次都是 TARGET_NOT_FOUND -> 询问目标描述或换搜索区域
如果上一次是 ERROR_FIELD_MISMATCH -> 优先修返回结构

向量数据库的局限，模糊语义匹配不等于精准查找
VECTOR DB LIMITS：向量数据库适合“口味偏好、历史对话”这种近似匹配，但 Agent 需要“手机号、精确属性、键值查找路径”这种精准查找。
结构化存储：SQLite / JSONL / dict，保存精确状态和键值
向量检索：只保存语义摘要，用来找相似失败、相似场景、相似经验

时间状态问题
上一次机器人位置：门口
当前机器人位置：会议室
上一次 VLN endpoint：192.168.31.43:8000
当前 VLN endpoint：127.0.0.1:8000
上一次张三位置：办公室
当前张三可能在走廊
如果 AgentMemory 只存“张三在办公室”而没有时间，就可能让机器人去旧位置找人。
所以每条记忆必须有时间状态：双时间协同

Skill 1：目标找不到后的二阶段策略

适用场景：Memory 显示同一目标连续多次 TARGET_NOT_FOUND。
name: target_not_found_second_pass
trigger:
  error_code: TARGET_NOT_FOUND
  repeat_count_gte: 3
steps:
  - 读取 target_context_view
  - 检查目标是否有最近有效位置
  - 如果有，先去最近有效位置附近搜索
  - 如果没有，询问上层目标衣着、位置或更多描述
  - 如果仍失败，返回明确失败原因
fallback:
  - 不继续无限重试同一个搜索动作
提升优点：让 Agent 从“重复失败”升级为“换策略搜索”。

Skill 2：返回结构标准化

适用场景：收到下游返回，字段可能是 success/result/error_msg/err_msg/command。
name: normalize_agent_response_contract
trigger:
  stage: response_normalize
steps:
  - 如果有 success，优先用 success
  - 如果没有 success 但有 result 且是 bool，用 result 映射 success
  - 如果 success=false，error_msg 必须非空
提升优点：消除 success=false 但 error_msg="" 的问题，给 ReAct 和人类复盘都提供明确依据。
