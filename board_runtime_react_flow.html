板端 Agent 跑通流程与 ReAct 复盘

这页按照真实机器人跑通链路组织：从 SSH 登上板端、启动传感器和导航、启动 Motion Agent，再由测试脚本把“找人”任务送进 8766，最终由 Agent 转发到 VLN 的 8000 接口并驱动 ROS2/Nav2。

ReAct 在这个系统里的位置

这里的 ReAct 可以理解成 Motion Agent 的“边想边做”：先把用户说的自然语言拆成任务，再选择工具执行，然后根据工具返回、VLN 返回、ROS2 状态、日志结果继续判断下一步。

在真实跑通链路里，ReAct 不应该替代 VLN 做视觉导航。更合理的分工是：Motion Agent 负责理解意图、选择任务、管理记忆、处理失败、决定是否重试；VLN 负责根据图像、地图、深度和语义信息输出具体导航动作；ROS2/Nav2 负责把动作落到机器人运动上。

一句话：Motion Agent 像任务调度员，VLN 像现场导航员，ROS2/Nav2 像执行机构。

当前跑通链路中的 ReAct 回合

  1. Thought：用户要“找张三”，Agent 判断这是一个导航找人任务。
  2. Action：选择工具 `go_find_person`，构造 `person_id=张三` 和 `user_prompt=请去找张三`。
  3. Observation：收到 VLN 的 `command`、`result`、`error_msg` 或超时日志。
  4. Reflection：如果成功就结束；如果失败，就判断是连接失败、协议字段不匹配、VLN 没启动、地图服务缺失，还是机器人执行失败。
  5. Next Action：根据失败类型决定重发、改写 prompt、请求停止、切换找物/找人协议，或者提示人去启动服务。

可以提升的方向

  • 给每一次工具调用加 `trace_id`，把 8766、8000、ROS2 action、日志文件串起来。
  • 把 `success/result/error_msg/command` 做成统一的返回结构，避免出现 `success:false` 但 `error_msg` 为空的情况。
  • 让 AgentMemory 保存最近失败原因，而不是只保存对话历史。
  • 给 ReAct 增加失败分类器：连接类、协议类、感知类、导航类、执行类、环境类。

失败返回的 log 怎么再推理

每次失败时，不要只看最后一行。更稳的做法是把失败看成一条链：用户指令是否送到 8766、Agent 是否选中正确工具、Agent 是否连上 8000、VLN 是否返回 command/result、ROS2/Nav2 是否接受动作、机器人是否真的执行。

再推理的核心是把 log 变成结构化观察结果。例如 `Connection refused` 属于连接失败，`result:false` 属于服务返回失败，`success:false error_msg:''` 可能是字段映射错误，`set_max_vel 服务不可用` 可能是导航依赖没启动。

例子 1：8766 成功但结果 false

{
  "success": false,
  "error_msg": "",
  "type": "go_find_person"
}

推理：这说明客户端已经连上 Motion Agent，任务也被执行到了某个返回点。`error_msg` 为空时，优先怀疑协议字段不统一，比如 VLN 返回的是 `result`，Agent 却只读 `success`。

下一步：看 `/userdata/roslog/agent/agent_*.log` 里有没有 `go_to_person`、`8000`、`result`。如果有 VLN 返回，就修字段映射；如果没有，则查 `LOCAL_MODEL_URI`。

例子 2：连不上 8000

无法连接到本地模型服务器:
ws://192.168.31.43:8000/ws/navigate

推理：机器人侧 Agent 已启动，但 VLN 服务器可能没开、IP 写错、网络不通，或者 8000 服务还在加载模型。

下一步：在 PRO6000 上确认 `bash start_vln.sh` 已经启动，并且日志看到 `Uvicorn running` 或 `Waiting for application startup` 后完成加载；在机器人上用简单 WebSocket 脚本测试 `192.168.31.43:8000`。

例子 3：VLN 有动作但机器人不动

{"command": "右转90度", "inference_time_ms": "1739.72 ms"}

推理：VLN 推理已经跑通，问题更可能在 ROS2/Nav2 或硬件侧。比如底盘没启动、导航 action 不可用、雷达/SLAM 没起来、坐标系异常。

下一步：机器人侧检查 `./start_base.sh`、`./lidar1.sh`、`./start_slam.sh`、`./start_nav.sh` 是否都在运行，再看 Nav2 action feedback 和内核日志。

复杂任务怎么提升完成能力和效率

复杂任务不要让 Agent 一口气把所有事情做完。更稳定的方式是拆成“任务图”：先确认目标，再启动必要服务，再执行导航，再验证结果，再决定是否继续。每一步都保存状态和失败原因。

效率提升的关键不是让模型说得更快，而是减少无效尝试：复用已经打开的 WebSocket 连接、缓存最近的人员/物体特征、把地图和视觉服务健康检查前置、让失败分类器直接给出下一步修复动作。

例子：找人后递交物品

  1. 先解析目标：找张三，并带着药盒过去。
  2. 检查药盒状态：如果没关好，先执行 `set_medicine_box_switch`。
  3. 执行 `go_find_person`：把任务转给 VLN。
  4. 到达后校验：如果人脸/特征不匹配，继续搜索，不要立刻结束。
  5. 完成交互：播放提示或打开药盒。

例子：巡检多个地点

  1. 把“巡检大厅、工位、会议室”拆成三个子任务。
  2. 每个子任务有自己的成功条件：到达、观察、记录、返回结果。
  3. 失败时不重跑全部任务，只重试当前地点。
  4. 把每个地点的观察写入 AgentMemory，最后统一总结。

例子：找不到目标时改策略

如果 VLN 多次返回找不到目标，Agent 可以改写策略：从“直接找张三”变成“先去张三常出现的位置，再进行人脸确认”。这时 ReAct 的价值就出来了：它不是盲目重复，而是根据观察结果调整下一步。

可以加入策略阈值：同一个目标连续两次失败后，查询对象库；连续三次失败后，换搜索区域；连续四次失败后，返回给上层 Agent 请求更多信息。
